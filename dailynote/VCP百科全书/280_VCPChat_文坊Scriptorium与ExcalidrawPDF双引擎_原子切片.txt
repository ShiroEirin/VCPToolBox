## 核心结论
「文坊」从「文档预览 + 白板」升级为**本地文件工作台**：`modules/scriptorium` 是一层可插拔的文件类型分发器（markdown / pdf / sheet / view / webPages），配合三个自带 vendor 依赖，把「打开任意本地文件并在应用内编辑」做成了内建能力，而非调用外部程序。

## 架构：一层分发 + 五类处理器
| 文件 | 作用 |
|---|---|
| `fileTypes.js` | 扩展名 → 类型的映射表 |
| `fileAccess/index.js` | 统一文件读取抽象 |
| `fileViews.js` | 类型 → 视图组件的解析 |
| `markdownFiles/index.js` | Markdown 处理器 |
| `pdfFiles/index.js` | PDF 查看入口 |
| `pdfFiles/edit.js` | PDF 编辑（基于 pdf-lib） |
| `pdfFiles/fonts.js` | PDF 字体嵌入处理 |
| `sheetFiles/index.js` | 表格文件处理器 |
| `viewFiles/index.js` | 只读视图类文件 |
| `webPages/index.js` | 网页文件处理 |
| `dropOpen.js` | 拖拽打开入口 |
| `textEncoding.js` | 文本编码探测与转换 |
| `atomicReplace.js` | **原子写入替换**（防写一半损坏原文件） |

## 三个 vendor 依赖的分工
- **`vendor/excalidraw`（19.23 MB / 238 文件）**：白板引擎，对应 PR #302 `scriptorium-board`——文坊的「板」能力来自它。
- **`vendor/pdfjs`（4.49 MB / 202 文件）**：PDF 渲染与解析，负责「看」。
- **`vendor/pdf-lib`（1.23 MB / 5 文件）**：PDF 结构化写入，配合 `pdfFiles/edit.js` 负责「改」。
- 三者全部**内置在仓库**，不依赖 CDN、不在运行时下载——离线可用，也避免版本漂移。

## 两个值得注意的工程细节
1. **`atomicReplace.js` 是写入安全的底座**：编辑器保存不是「先删除再写」，而是先写临时件再原子替换；这是文件工作台最容易出事故的地方（断电／崩溃留下半截文件），单独抽模块是对的。
2. **`textEncoding.js` 单独成文件**：说明「打开本地文件」第一道坑是编码判定（GBK/UTF-8/BOM），把它抽出比在每个处理器里重复判断更稳。
3. **`dropOpen.js` 独立**：拖拽是入口而非某类型专属，因此与类型表解耦。
