一、解决的问题

长文本切分与清洗此前在超长输入上会长时间占用主线程，导致 Event Loop 阻塞——表现为整个服务「卡住」而不是「变慢」。本轮两条线同时改：切分改成**零回溯线性**，清洗改成**有界 LRU 记忆化**。

三、有界缓存键生成（代码注释原文）

```text
生成定长有界缓存键（纯 JS 实现，100% 兼容 tests/textChunker.test.js 的 VM 沙箱环境）：
<= 64KB 直接使用原字符串；> 64KB 使用双 32-bit FNV-1a 哈希 + 长度 + 首尾采样，
避免大字符串常驻内存同时支持任意长度缓存。
```

设计要点：
1. **≤64KB 直接用原串**——避免小文本白付哈希成本；
2. **>64KB 用双 32-bit FNV-1a 哈希 + 长度 + 首尾采样**——定长键，大串不常驻内存；
3. **纯 JS 实现**——为的是能在 VM 沙箱里跑测试，不依赖 Node 原生 crypto。

四、TextSanitizer 的有界 LRU（实测常量）

```js
const SANITIZE_CACHE_MAX_SIZE = 512;
const DIRECT_KEY_MAX_CHARS = 65536;
const SANITIZE_VALUE_MAX_CHARS = 5000000;
const stripHtmlCache = new Map();
const sanitizeEmbeddingCache = new Map();
```

| 常量 | 值 | 含义 |
|---|---|---|
| `SANITIZE_CACHE_MAX_SIZE` | 512 | 缓存条目上限 |
| `DIRECT_KEY_MAX_CHARS` | 65,536 | 键直接使用阈值（与 TextChunker 一致） |
| `SANITIZE_VALUE_MAX_CHARS` | 5,000,000 | **单值 5MB 硬上限** |

超长键改用 SHA-256 摘要：

```js
function toBoundedCacheKey(rawKey) {
    if (typeof rawKey !== 'string' || rawKey.length === 0) return '';
    if (rawKey.length <= DIRECT_KEY_MAX_CHARS) return rawKey;
    const digest = crypto.createHash('sha256').update(rawKey).digest('hex');
    return `__sha256:${rawKey.length}:${digest}`;
}
```

键格式 `__sha256:<原长度>:<hex摘要>` —— 带上原长度是为了降低哈希碰撞时的误命中概率。

七、风险

1. **85% 安全边界是硬编码比例**：换模型后若 `WhitelistEmbeddingModelMaxToken` 未同步，实际可用 token 会偏小或偏大。
2. **5MB 单值上限**：超过 `SANITIZE_VALUE_MAX_CHARS` 的清洗结果会被拒（具体行为需按调用侧处理），超大 HTML 文档需先分片。
3. **FNV-1a 双 32-bit 是弱哈希**：碰撞概率高于 SHA-256，但配合「长度 + 首尾采样」已足够；若缓存命中出现内容错乱，优先怀疑这里。
4. **LRU 上限 4096 / 512**：高频多样本场景下命中率会下降，属于「用内存换确定性」的取舍。
