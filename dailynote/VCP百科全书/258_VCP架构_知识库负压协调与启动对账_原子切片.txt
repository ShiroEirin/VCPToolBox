一、解决的矛盾

启动阶段原本有两条扫描来源：Rust 侧 watcher 的 `initialScan`，和 JS 侧的 `_reconcileAfterOverflow()`。两者同时跑，会对同一批文件重复派发 add 事件，在高负载时形成「自己压自己」的背压竞态。

二、改动：启动只留一次对账（fileWatcher.js，原文注释）

```js
// Startup uses the single reconciliation below, including indexed
// paths for missing-file detection. Do not also launch a native scan.
initialScan: false,
```

对应的 JS 侧：

```js
// One authoritative startup scan, with the indexed-path snapshot.
// Real overflow recovery remains independently enabled.
if (config.fullScanOnStartup !== false) {
    void this._reconcileAfterOverflow();
}
```

要点：`initialScan` 被硬置为 `false`，不再由 `config.fullScanOnStartup` 驱动；开关语义整体上移到 JS 单点。真实的溢出恢复（`_handleRustEvent()` 内）保持独立可用，不受该开关影响。

八、风险

1. `initialScan` 硬置 false 后，若 `_reconcileAfterOverflow()` 自身失败，启动将没有第二道兜底扫描。部署时若发现启动后索引缺失，应优先查看 JS 侧对账日志而非 Rust watcher。
2. `fullScanOnStartup` 语义已上移，旧配置项仍被读取但不再控制 Rust 侧行为，属于「保留键名、收窄语义」。
