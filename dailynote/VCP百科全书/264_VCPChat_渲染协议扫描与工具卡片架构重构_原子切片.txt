一、三次提交合起来做的事

把「工具调用块怎么被识别、怎么被渲染、流式过程中边界怎么稳定」这三件原本混在 `messageRenderer.js` 里的事，拆成三个独立层：

```text
协议识别层  toolRequestScanner.js        ← 判断哪段文本是协议、哪段是普通文本/代码
呈现映射层  toolPresentation.js          ← 工具名 → 卡片形态
主题面层    projectForgeTopicSurface.js  ← ProjectForge 话题的专属呈现
流稳定层    streamManager.js             ← 流式增量与稳定边界
```

二、协议识别层（toolRequestScanner.js）关键语义

该文件不是本轮新建（`--diff-filter=A` 指向 `0a8a2576`），本轮 b322c4fb 对它 +17 行。它当前 438 行，核心是「哪些 `<<<[TOOL_REQUEST]>>>` 是真的协议」：

1. **反引号包裹视为字面量**：`` `<<<[TOOL_REQUEST]>>>` `` 不建立协议块；
2. **代码域优先遮蔽**：fenced code 与行内 code span 内的标记不算协议。注释原文解释了行内 code span 的限制理由——

```text
行内代码域额外限制为同一行。Markdown code span 虽可容纳换行，但聊天
正文中的颜文字（如 `(・`ω´・)`）常含不成对反引号；若允许它与数百字后
工具载荷中的反引号跨行配对，会把真实 TOOL_REQUEST 错误覆盖为代码示例。
```

3. **工具结果数据域优先级最高**：`collectToolResultRanges` 先遮蔽结果区，其内部任何 `TOOL_REQUEST` / `DESKTOP_PUSH` 都不具协议含义，也不会与外部正文的反引号配对吞掉后续真实协议块；
4. **容错结束标记**：`/<{2,4}\[END_TOOL_REQUEST\]>{2,4}/gi` —— 允许左右各 2–4 个尖括号，因为后端语义解析偶尔多/少尖括号，但中间的协议名保持严格；
5. **字段感知扫描**：`scanToolRequestEnd` 返回三态 `complete` / `incomplete-field` / `incomplete-request`；进入字段后，`<<<[END_TOOL_REQUEST]>>>` 只被当作字段载荷，必须先遇到与括号风格严格对应的 `「末」` 或 `}末}`（含 `ESCAPE` 变体）。
