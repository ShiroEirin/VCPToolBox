## 核心结论
ChatKernelV2 不是「新功能」，而是给聊天加了**三层行政机制**：谁能发言（admission）、谁能生成（lease）、消息怎么落盘不丢（relay / history CAS / persistence）。作者把它称为「超级重构」并配了「端到端高并发压测」——说明目标是在并发场景下不再丢消息、不再双答、不再抢写。

## 三层职责（自模块名与文件分布倒推）
| 层 | 模块 | 解决的问题 |
|---|---|---|
| **准入** | `topicMessageAdmission`(721) + `topicAdmissionSingleChat`(82) + `topicAdmissionGroup`(55) + `topicMessageAdmissionHost`(152) + `topicMessageAdmissionStore`(56) | 同一话题下消息/请求的**排队与去重**；单聊与群聊两套入口；Host 做宿主侧调度，Store 做持久化 |
| **租约** | `topicGenerationLease`(57) | 「同一次生成只允许一个持有者」——防止多个请求同时为同一话题生成（双答/串话） |
| **中继与一致** | 测试面：`topic-relay`(446) / `topic-history-cas`(mjs) / `topic-terminal-persistence`(46) / `topic-stream-uncertain`(97) / `topic-owner-history-barrier` / `topic-manual-continue` / `topic-conversation-resolver` | 中继投递、历史 CAS、终端消息落盘、**流式状态不确定**的收口、历史屏障 |

## 从测试文件反推的硬约束（重要）
新增测试本身就是规格说明书：
- `topic-generation-lease`：生成租约存在且互斥。
- `topic-standalone-lease`(159)：独立会话下的租约行为。
- `topic-history-cas`：历史写入用 **CAS（比较并交换）**，防并发覆盖。
- `topic-owner-history-barrier`：属主历史屏障——其他人不能越权写。
- `topic-stream-uncertain`(97)：**流式结果不确定**时如何收敛（中断/超时/部分到达）。
- `topic-manual-continue`：手动续写与自动生成的边界。
- `topic-relay`(446) + `topic-relay-persistence-integration` + `topic-relay-renderer`：中继在**主进程/持久层/渲染层**三边一致。
- `topic-sponsor-delivery`(180) / `topic-sponsor-retired-entry`(27) / `topic-sponsor-service-routing`(71)：话题发起（sponsor）的投递与退役入口。
- `topic-agent-delete-updates` / `topic-group-delete-updates`：删除话题后各端更新。
- `topic-message-admission` / `topic-message-admission-host` / `topic-message-admission-store`：三层准入各自可测。
- `topic-admission-renderer-failure` / `topic-admission-single-chat` / `topic-admission-group` / `topic-admission-queue-view`：**渲染层失败**也要能正确拒绝准入。
